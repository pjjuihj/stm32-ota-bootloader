## 1. 我犯的错误

### 1.1 假设硬件配置（最严重）

**错误：**
- 假设 PA0 按键是低电平有效
- 没有先确认硬件配置
- 直接写代码

**后果：**
- PA0 检测不工作
- 浪费大量调试时间
- 用户反复修改代码

**正确做法：**
```
第一步：问用户
├─ PA0 按键怎么接的？
├─ 按下是高电平还是低电平？
├─ 有没有外部电路？
└─ 万用表测量结果是多少？

第二步：测量验证
├─ 未按下时电压是多少？
├─ 按下时电压是多少？
└─ 确认电平逻辑

第三步：再写代码
└─ 根据实际配置编写
```

**教训：**
> **不要假设，要确认。**
> 嵌入式开发中，硬件配置是基础。
> 基础错了，上面的代码全白写。

### 1.2 手动跳转不可靠

**错误：**
```c
// 手动跳转到 0x08000000
SCB->VTOR = 0x08000000;
__set_MSP(bootloader_sp);
jump_to_boot = (pFunction)(bootloader_reset | 1);
jump_to_boot();
```

**后果：**
- Bootloader 没有正常启动
- LED 长亮，OLED 不刷新
- 外设状态不干净

**正确做法：**
```c
// 使用复位方式
NVIC_SystemReset();
```

**教训：**
> **复位比手动跳转可靠。**
> 手动跳转需要处理很多细节：
> - 时钟配置
> - 外设状态
> - 中断状态
> - 向量表
>
> 复位让硬件自动处理这些，更安全。

### 1.3 没有防误触机制

**错误：**
- 短按就触发跳转
- 没有考虑误操作
- 用户体验差

**后果：**
- 用户误触导致意外跳转
- 数据丢失风险

**正确做法：**
```c
// 长按检测
uint32_t press_start = HAL_GetTick();
while (按钮按下) {
    HAL_Delay(10);
    if (HAL_GetTick() - press_start >= 2000) {
        // 长按 2 秒，触发操作
    }
}
```

**教训：**
> **用户会误操作，要防御。**
> 关键操作需要确认机制：
> - 长按检测
> - 双击确认
> - 软件锁
> - 硬件保护

### 1.4 OLED 进度条不更新

**错误：**
- 只在 ota_start 时设置进度
- 接收数据时没有更新显示
- 进度条看起来不动

**后果：**
- 用户不知道进度
- 体验差
- 以为程序卡死

**正确做法：**
```c
// 在数据处理中更新显示
boot_config.received_size += data_len;
uint8_t progress = boot_config.received_size * 100 / boot_config.app_size;
Display_OTA_SetProgress(progress);
Display_OTA_SetSize(boot_config.received_size, boot_config.app_size);
```

**教训：**
> **显示更新要在数据处理中调用。**
> 不要只在初始化时设置。
> 实时反馈很重要。

---

### 1.5 OLED 刷新太慢

**错误：**
- 每次进度更新都调用 OLED_Refresh()
- 刷新整个 128x64 屏幕
- I2C 传输慢

**后果：**
- 进度条更新慢
- 看起来卡顿

**正确做法：**
```c
// 只在进度变化时更新
static uint8_t last_progress = 255;
if (progress == last_progress) return;
last_progress = progress;
// ... 更新显示
OLED_Refresh();
```

**教训：**
> **减少不必要的刷新。**
> 使用脏标记（dirty flag）。
> 只更新变化的部分。

## 2. 反思

### 2.1 开发流程问题

**问题：**
- 没有先确认硬件配置
- 没有测试单个模块
- 直接集成所有功能

**正确流程：**
```
第一天：确认每个外设单独工作
├─ 测试 PA0 电平
├─ 测试 LED 控制
├─ 测试 UART 通信
└─ 测试 OLED 显示

第二天：打通数据链路
├─ Bootloader 接收数据
├─ Flash 擦写
├─ CRC 校验
└─ 分区切换

第三天：集成显示
├─ OLED 初始化
├─ 进度条显示
├─ 错误提示
└─ 完整流程
```

### 2.2 调试效率问题

**问题：**
- 靠猜而不是测量
- 没有添加调试输出
- 测试不充分

**正确做法：**
```
1. 先加调试输出
├─ 打印 PA0 状态
├─ 打印跳转地址
└─ 打印错误信息

2. 使用工具测量
├─ 万用表测量电压
├─ 逻辑分析仪看波形
└─ 示波器看时序

3. 逐个测试
├─ 测试 PA0 检测
├─ 测试跳转逻辑
├─ 测试 Bootloader 启动
└─ 测试完整流程
```

### 2.3 代码质量问题

**问题：**
- 没有边界检查
- 没有错误处理
- 没有注释

**改进：**
```c
// 添加边界检查
if (progress > 100) progress = 100;

// 添加错误处理
if (!check_bootloader_exists()) {
    uart_send_line("[ERROR] No valid bootloader!");
    return;
}

// 添加注释
/* 消抖：等待 50ms */
HAL_Delay(50);
```

## 3. 教训总结

### 3.1 嵌入式开发铁律

```
1. 不要假设硬件配置
   └─ 先测量，再写代码

2. 先测单个模块
   └─ 确认每个外设单独工作

3. 复位比手动跳转可靠
   └─ 使用 NVIC_SystemReset()

4. 用户会误操作
   └─ 添加长按检测

5. 实时反馈很重要
   └─ 显示更新要在循环中
```

### 3.2 调试技巧

```
1. 先加调试输出
2. 使用万用表测量
3. 逐个测试模块
4. 记录错误和修复
5. 反思总结教训
```

### 3.3 代码质量

```
1. 添加边界检查
2. 添加错误处理
3. 添加注释
4. 使用有意义的变量名
5. 保持代码简洁
```
